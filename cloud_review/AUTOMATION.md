# Cloud bill processing

The owner journey is: sign in, drop one supplier PDF, watch processing, open the resulting Zoho bill. No manual data entry or laptop process is involved. New uploads enter a persistent queue. Uploading the same PDF opens its retained result without creating another job or repeating extraction. An invoice already in Zoho is labelled duplicate only after read-only source reconciliation; a mismatching reused number is held without a financial write.

The cloud worker reuses the existing vendor, GST routing, payload and exact read-back functions in `src/zoho_bills.py`. That file and the installed Windows program are unchanged. Two separate Haiku readings must agree on the invoice identity, printed buyer/supplier GSTIN, dates, currency, every charge amount/rate/SAC and printed totals. Missing or unclear source values, multiple invoices, inconsistent GST or Zoho tax-group rounding stop creation. Foreign-currency FX remains held until the accounting rate is approved; INR overseas bills use the existing reverse-charge logic. Existing account mappings are preserved, not inferred by AI.

Before each create, the worker queries all bills of the matched supplier, including identifier variants. It records source SHA256, exact payload, owner policy and posting state before sending the request. A lost create response triggers a lookup, never a second create. Recovery requires the unique upload/source marker on the matching bill. Completion requires exact financial read-back and the original PDF attached and downloaded with the same hash. Failure does not silently retry financial writes or paid extraction.

The owner approved Debian `poppler-utils` solely for local `pdfinfo`/`pdftotext` source corroboration. It is a GPL-licensed system package, with no licence fee, subscription or extra AI provider. The container installs it during build and needs normal package/security maintenance. Python's standard library cannot reliably extract these PDFs. No pip dependency, new OCR/AI service, database migration, payment action, existing-bill correction or Windows cache change. Queue, parse evidence and cost reservations are private files beside the existing cloud SQLite database; corrupt/missing state fails closed. An OS file lock permits one worker. Keep one replica and zero deployment overlap.

Automatic input is limited to 5,000,000 bytes and 20 readable text pages before paid calls. The owner GSTIN is not supplied to Haiku in its prompt. Both readings must also be corroborated against locally extracted, labelled invoice identity and currency, the buyer's registration in its own printed column/block, invoice/due dates, subtotal/payable/GST totals and distinct charge rows with matching amounts/rates. PO references, shipper registrations, reference currency and reused charge occurrences cannot substitute for those fields. Existing deterministic CMA/BL guards are reused. Missing, ambiguous or scanned text holds the original. These checks do not prove universal OCR/extraction accuracy or override unsupported accounting cases. Zero-rated line tax mappings, printed adjustments and FX remain explicit holds until their exact accounting treatment is supported and evidenced.

Temporary safe-read failures receive at most three automatic backoff retries. The owner can retry a classified transient failure from its private status page using the existing secure session and CSRF token. Completed readings are reused; a missing reading requires the explicit retry and available budget. An uncertain create only looks up its original outcome, including after manual retry/restart. A proven Zoho rejection retains its code/reason and cannot be mistaken for success. Created bill IDs and attachment-attempt evidence survive recovery; an existing original is checked before another attachment upload. Real mismatches stay held. Upload enqueueing does not share the provider-call lock. Worker errors remain visible in a failing health check while the scan loop survives and can recover.

The upload's exact policy/id/hash intent is committed atomically with its original in the existing suggestions table. Recovery only enqueues these explicitly authorized intents; old manual uploads are excluded. Journals and budget reservations sync their parent directory on POSIX before external effects. Transfer the existing private tax/vendor rules as `ZOHO_TAX_RULES_JSON` and `ZOHO_VENDOR_RULES_JSON`; cloud import refuses absent or malformed rules rather than silently substituting defaults.

Deployment uses repository-root Docker context and `cloud_review/Dockerfile`. Existing owner credentials, private `/data/owner` storage, service caps, backups and authorized expiry must be retained. Enable only after acceptance: `APP_AUTOMATION_POLICY=owner-cloud-automatic-posting-2026-10-28`, `APP_AUTOMATION_POSTING=1`, existing `ANTHROPIC_API_KEY` and Zoho `ZOHO_CLIENT_ID`, `ZOHO_CLIENT_SECRET`, `ZOHO_REFRESH_TOKEN`, `ZOHO_ORGANIZATION_ID` configured privately. `APP_AI_BUDGET_USD` must be a positive value no greater than1.00 within the remaining owner budget. Do not commit any values. Absence of the policy leaves the previous isolated review mode intact. Posting off supports live extraction/validation acceptance before new financial records are created.

Haiku4.5 standard published rates checked28 October2026: USD1/M input, USD5/M output. Free token counting precedes each paid call; input capped40000, output6000, no caching surcharge, 25% input reservation margin. After a response with complete valid provider usage, its reservation settles to the reported token cost; unknown/failed outcomes retain their full reservation. Prior spent/unresolved amounts and call counters are never reset on restart. This is an application allowance, not a final provider invoice or guarantee about unrelated account spending. The currently approved USD0.50 allowance and service expiry remain unchanged. The owner permits revisiting the INR500 planning ceiling for the express costs of starting, running and maintaining cloud automation, with each efficient new budget submitted for approval before incurring it. No new numerical allocation, credit purchase, subscription or service extension was approved by that instruction alone.

Tests: `python -m unittest discover -s cloud_review -p 'test_*.py' -v`. Offline tests use synthetic PDFs and fake providers; they do not establish live extraction accuracy or live Zoho acceptance. Those results must be recorded separately.
